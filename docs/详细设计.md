# 详细设计

> 怀化国际陆港冷链资源智能撮合平台（实验室硬件原型 + 港区规模虚拟）
> 本文档与当前代码实现保持一致（含 IoT、遥测、支付结算、数字孪生、评价、鉴权与部署方案）。

---

## 一、系统总体架构

```
┌──────────────────────────────────────────────────────┐
│ 展示层  Vue3 + TypeScript + Three.js(数字孪生) + ECharts │
│        数字孪生大屏 / 运营管理（资源·市场·订单）           │
├──────────────────────────────────────────────────────┤
│ 应用层  FastAPI 单体服务                                │
│        认证 / 资源 / 订单 / 撮合 / IoT / 设备 / 评价      │
│        支付 / 结算 / 数字孪生 / 后台任务                  │
├──────────────────────────────────────────────────────┤
│ 数据层  MySQL 8（业务数据） + Redis 7（缓存与实时值）      │
├──────────────────────────────────────────────────────┤
│ 接入层  EMQX 5（MQTT） ← ESP32 传感器 / Python 模拟器     │
└──────────────────────────────────────────────────────┘
```

**主数据流**：
传感器采集 → MQTT(`iot/{device_code}/data`) → FastAPI 订阅入库 → Redis 最新值(TTL 5s) → WebSocket 广播 → 大屏/孪生实时刷新。

**事务外盒流**：
业务写事务 → 同事务登记 `outbox_events` → 后台任务投递 → WebSocket 广播，保证业务提交与事件推送最终一致。

**支付流**：
创建支付意图 → 沙箱收银台/支付宝回调 → `payment_events` 去重入账 → 更新 `payment_status` → 登记 `order_paid` 事件。

## 二、技术栈

| 层次 | 选型 | 说明 |
|---|---|---|
| 后端框架 | FastAPI 0.143 | 单体服务，自动 OpenAPI 文档 |
| ORM / 迁移 | SQLAlchemy 2.1 + Alembic 1.20 | 表结构由迁移管理，应用启动不建表 |
| 数据库 | MySQL 8.0 | utf8mb4，业务主库 |
| 缓存 | Redis 7 | 键前缀 `hlg:`，资源列表/详情/撮合/最新遥测 |
| 消息接入 | EMQX 5.7 + paho-mqtt | MQTT 订阅在独立后台线程 |
| 实时推送 | WebSocket | 进程内 BroadcastHub，跨线程安全投递 |
| 前端 | Vue 3.5 + Vite 8 + TypeScript | Pinia 状态、vue-router 哈希路由 |
| 3D 孪生 | Three.js 0.186 | GLTFLoader + DRACOLoader，程序化 GLB 模型 |
| 图表 | ECharts 6 | IoT 趋势曲线 |
| 容器化 | Docker Compose | 6 个服务，含健康检查 |

## 五、API 接口设计

共 65 个路径（63 个业务路由 + 健康检查 + WebSocket），完整定义以 `/openapi.json` 为准。

### 5.1 认证与用户

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | /api/v1/auth/register | 公开 | 注册；密码需 ≥8 位且含字母与数字；admin 角色不开放自助注册 |
| POST | /api/v1/auth/login | 公开 | 登录，返回 access + refresh token；含失败限流 |
| POST | /api/v1/auth/refresh | 公开 | 用 refresh token 换取新 token 对（无感续期） |
| POST | /api/v1/auth/change-password | 登录 | 修改密码（校验旧密码与强度） |
| GET | /api/v1/users/me | 登录 | 当前用户 |
| PUT | /api/v1/users/me | 登录 | 更新企业名/联系方式 |

## 六、核心业务规则

### 6.1 撮合评分（2.0）

对 `status = available` 的资源打分排序（候选上限 200），满分 **120**，总分与八项分项、中文理由一并返回：

| 维度 | 上限 | 计算方式 |
|---|---|---|
| 价格得分 | 30 | 候选集内最低价得满分，最高价得 0，线性递减 |
| 信用得分 | 20 | `20 × clamp((credit - 60) / 40, 0, 1)` |
| 时间窗口 | 20 | 剩余覆盖天数 × 2，上限 20 |
| 类型匹配 | 10 | 指定 `type` 且命中 +10 |
| 供给方口碑 | 15 | 评价均分 3 → 0，5 → 15；无评价给 9 分中性值 |
| 成交热度 | 10 | 近 30 天非取消订单数，按候选集最大值归一化 |
| 上新程度 | 5 | `5 × clamp(1 - 上架天数 / 30)` |
| 个性化偏好 | 10 | 登录用户近 50 单需求类型命中 +10 |

- 排序：总分降序，同分按价格升序
- 推荐理由：价格最低档、信用 ≥ 95、窗口 ≥ 7 天、口碑 ≥ 4.5、近 30 天成交 ≥ 5 单、3 天内新上架、命中历史偏好
- 未登录请求不含个性化维度，结果与登录用户分开缓存
- 结果缓存 30 秒（键 `hlg:match:recommend:{type}:{max_price}:{top_n}:{uid}`，Redis 不可用时直算降级）

### 6.2 订单状态机与资源联动

```
inquiry/pending ──确认──► confirmed ──开始──► ongoing ──完成──► finished ──结算──► settled
      │                      │                     │
      ├──驳回──────────────► rejected              │
      ├──取消──────────────► cancelled ◄───────────┘
      └──超时 48h──────────► expired
```

- 允许流转：`inquiry|pending → confirmed|rejected|cancelled|expired`、`confirmed → ongoing|cancelled`、`ongoing → finished|cancelled`、`finished → settled`；终态 `settled/rejected/cancelled/expired` 不可再流转
- 操作人角色：`confirmed/rejected/ongoing/finished` 仅供给方或管理员；`settled` 仅管理员；`cancelled` 三方均可；`expired` 仅管理员
- 非订单参与方且非管理员操作 → 403；角色不在允许集合 → 403；非法流转 → 400
- 并发控制：更新时以 `version` 做 CAS（`WHERE version = :old`），冲突返回 409，由前端刷新后重试
- 创建订单：行锁资源（`SELECT ... FOR UPDATE`），校验 `available`、可用窗口与时段重叠，按天计费（不足一天按一天），锁定当时 `commission_rate`；资源 `available → booked`
- 订单转 `finished`：写入 `commission = total_price × commission_rate`，并按 `order_id` 幂等生成结算单（pending，`payable = amount − commission`）
- 订单转 `cancelled` / `rejected` / `expired` / `finished`：仅当该资源无其他活跃订单（`pending/confirmed/ongoing`）时，`booked → available`
- 每次状态变更登记 outbox 事件（`order_status_changed` + `resource_updated`），驱动大屏冷链箱颜色刷新
- 超时清理：后台任务将 `pending/inquiry` 超过 48 小时未确认的订单置为 `expired` 并释放资源

### 6.3 幂等键

- 创建订单支持 `Idempotency-Key` 请求头，作用域 `create_order`
- 首次请求写入 `idempotency_keys`（status=processing）；成功后置 `done` 并缓存响应码与响应体
- 同键重复请求：若已 `done` 直接回放首次响应（不重复下单）；若仍 `processing` 返回 409
- 业务失败回滚时释放占位，允许客户端用同一键重试

### 6.4 事务外盒（Outbox）

- 订单/资源/支付变更在**同一数据库事务**内写入 `outbox_events`（status=pending），事务提交即保证事件不丢
- 后台任务周期拉取 pending 事件（按 id 顺序，单批 ≤100），通过 `BroadcastHub` 投递后置 `published`
- 投递失败 `retry_count + 1`，达到 5 次置 `failed` 并记录 `last_error`，便于人工排查
- 事件类型：`order_created` / `order_status_changed` / `order_paid` / `order_refunded` / `resource_updated` 等

### 6.5 支付与结算

- 支付模式由 `PAYMENT_MODE` 控制：`sandbox`（默认，模拟收银台）/ `off`（关闭，创建交易直接报错）
- 创建支付意图生成 `trade_no`（`SBX{order_id}-{毫秒}`）与 `pay_url`；重复创建对已支付订单返回 `already_paid`
- 回调按 `(provider, provider_txn_id)` 唯一约束去重，重复通知不会重复入账
- 支付结果写 `orders.payment_status`（paid / refunded / closed）并登记 `order_paid` / `order_refunded` 事件；**不改变履约状态**
- 结算单状态独立流转：`pending → confirmed → paid`，`pending/confirmed` 可 `void`；转 `paid` 时写入 `settled_at`
- 按日对账汇总订单数、GMV、平台佣金、已支付金额与待打款金额，供财务核对

### 6.6 遥测接入与告警去抖

- 窄表存储：一次上报最多 50 个点位，按 `(device_id, point_key, ts)` 去重，断网补传可安全重放
- 点位字典：内置 11 类点位（温度/湿度/门磁/电流/功率/电量/CO₂/信号/振动等），未注册点位返回 400；内置点位首次上报自动注册
- 越限去抖：连续 3 个采样同向越限才产生告警；数值回到正常区间自动关闭事件与活动告警
- 告警去重：同设备同类型告警 10 分钟内只保留一条
- 门磁变位（开/关）各记一条 `device_events`，用于进出库与失温溯源
- 状态正交：`status` 表示设备可用性（online/offline/degraded/alarm/maintenance/unknown），`quality` 表示数据新鲜度（good/stale/bad/unknown），二者独立推导

### 6.7 孪生绑定与状态汇总

- 孪生节点通过 `twin_bindings` 绑定设备点位，节点展示值取该点位最新一条遥测
- 单节点状态 = 绑定设备状态的最差值；设备 `online` 但数据 `stale/bad` 时降级为 `degraded`
- 容器节点（园区/库区/库房）自上而下继承子节点最坏状态，保证大屏任一层级都能看出异常
- 节点按 `node_key` 幂等 upsert，写入时校验父节点存在、空间存在且不构成环

### 6.8 信用分重算

评价提交后按被评价人收到的**全部评价**确定性重算，避免增量漂移：

```
无评价      → 100
有评价      → clamp(round(60 + 40 × (平均分 - 1) / 4), 0, 100)
```

即 5 星 = 100 分，1 星 = 60 分，4 星 = 90 分。

### 6.9 预警规则

- 阈值按「资源级规则 → 全局规则 → 系统配置（`ALERT_TEMP_MIN/MAX`、`ALERT_HUMIDITY_MAX`）」顺序生效
- 温度低于下限或高于上限 → `critical`；湿度高于上限 → `warn`
- 规则可在「告警处理 → 告警规则」页维护，支持按资源覆盖、停用与恢复默认
- 同设备同类型告警 10 分钟内只记一条
- 遥测链路（`/api/v1/iot/telemetry`）额外做连续 3 次同向越限去抖，见 6.6
- 运营人员标记已解决后状态置为 `resolved`，并推送 `alert_resolved`，大屏活跃告警即时移除

### 6.10 资源审核流程

```
发布 → pending ──管理员通过──► available ──属主下架──► offline
            └──管理员驳回──► offline ──属主修改后重新提交──► pending
```

- 新发布资源固定为 `pending`，市场不可见、不可下单
- 属主不能自行把 `pending` 改成 `available`（返回 403），必须由管理员审核
- 只有 `pending` 资源可审核；重复审核返回 400

### 6.11 设备离线检测

- 后台协程每 30 秒扫描一次在线设备
- `last_seen_at` 早于 `DEVICE_OFFLINE_SECONDS`（默认 90 秒）或从未上报 → 置为 `offline`
- 设备再次上报数据时自动恢复 `online`

### 6.12 安全与账号

**登录失败限流**：

- 同一用户名连续失败超过 `LOGIN_MAX_ATTEMPTS`（默认 5）次后锁定 `LOGIN_LOCK_SECONDS`（默认 900 秒）
- 锁定期间返回 429；Redis 不可用时自动降级为不限流，不阻断正常登录
- 登录成功即清除失败计数

**令牌与无感续期**：

- 登录返回 `access_token`（默认 24 小时）+ `refresh_token`（默认 7 天）
- 前端请求遇 401 时自动用 refresh token 换取新 token 对并重试原请求；并发 401 合并为单次刷新
- 刷新令牌仅能用于 `/api/v1/auth/refresh`，不可当作 access token 使用（通过 `type` 声明区分）

**修改密码**：

- 需提供旧密码校验；新密码 ≥8 位且含字母与数字；新旧不能相同
- 修改后旧密码立即失效

**审计日志**：

- 登录成功、修改密码、资源审核、用户角色/启用变更、告警处理均写入 `audit_logs`
- 记录操作人、动作、目标对象、变更描述与来源 IP
- 仅管理员可查询，支持按动作/用户名筛选与分页

| `order_created` | 新建订单 | 刷新订单列表 |
| `order_status_changed` | 订单状态变更 | 局部更新订单状态 |
| `order_paid` | 支付成功 | 刷新订单支付状态与结算入口 |
| `order_refunded` | 退款完成 | 刷新支付状态 |
| `resource_updated` | 资源状态变化 | 刷新资源列表，驱动 3D 配色 |
| `alert_resolved` | 告警被标记已处理 | 从大屏活跃告警中移除 |

### 7.2 跨线程广播

MQTT 订阅线程与 HTTP 线程都会发布事件，`BroadcastHub` 通过线程 ID 判断：
主线程用 `ensure_future`，其他线程用 `run_coroutine_threadsafe` 投递到主事件循环。

> 因广播与订阅均在进程内，后端必须**单进程**运行（`--workers 1`），否则 WS 客户端收不到其他进程产生的事件。

#### 8.1.1 替换为真实模型

现有 5 个 GLB 为程序化生成的占位资产，接口层不区分来源，按下面的约束替换文件即可，**无需改代码**：

| 约束 | 要求 |
|---|---|
| 文件路径 | `frontend-vue/public/models/<name>.glb`，文件名保持不变 |
| 坐标系 | Y 轴向上，单位米，模型原点位于底面中心 |

| 节点命名 | 顶层节点必须包含 `Body`（状态着色目标）与 `Sensor_*`（设备挂点） |
| 材质 | PBR（Metallic-Roughness），贴图打包进 GLB（推荐 Draco 压缩） |
| 面数 | 单模型 ≤ 20 万三角面，纹理 ≤ 2048×2048 |

替换步骤：

1. Blender 导出 glTF 2.0（`.glb`，勾选「应用修改器」「+Y 向上」）
2. 覆盖 `public/models/` 下同名文件，刷新大屏
3. 看浏览器控制台的 `[3D] 模型加载成功: <type> ... 尺寸 24.35×8.68×19.23m，mesh 100`，核对包围盒与 mesh 数
4. 若模型偏大/偏小或浮空，只改 `src/config/scene.ts` 中的位置/缩放常量

### 8.2 交互与联动

- 场景核心封装在 `src/core/ColdStorageScene.ts`，与 Vue 组件解耦
- 每个物件节点写入 `userData.resource_id / name / type / status`
- Raycaster 点击拾取 → 回溯父节点 → 弹出 AnchoredPopup（屏幕投影跟随）
- 点击弹窗展示：名称、状态、类型、位置、价格、绑定设备的温度/湿度/更新时间
- 资源状态配色：available 绿 `#00ff88`、booked 橙 `#ff9f43`、offline 红 `#ff4757`、pending 蓝 `#409eff`
- 模型缺失时自动回退为程序化几何体，不影响功能

### 8.3 孪生数据来源

- 大屏初始化调用 `GET /api/v1/twin/snapshot`，一次拿到节点树、按状态分组的设备、活跃告警与最近事件，避免首屏多次请求
- 节点树来自 `twin_nodes`，节点状态由绑定设备的 `status` 与 `quality` 聚合；容器节点继承子节点最坏状态
- 节点展示值取 `twin_bindings` 绑定点位的最新遥测（`telemetry` 窄表）
- 运行期增量由 WS `telemetry` / `twin_event` / `alert_resolved` 驱动，大屏无需轮询
- 空间树前端可直接使用 `GET /api/v1/twin/spaces`，与孪生节点解耦（空间是物理结构，节点是渲染结构）

## 九、安全设计

| 项 | 方案 |
|---|---|
| 密码存储 | PBKDF2-HMAC-SHA256，10 万次迭代，随机盐 |
| 密码强度 | 注册时校验 ≥8 位且同时含字母与数字 |
| 令牌 | JWT HS256，默认 24 小时，密钥来自环境变量且强制必填 |
| 权限模型 | 三角色 supplier / demander / admin + `require_admin` 依赖 |
| 账号状态 | `is_active` 为假时所有接口返回 403 |
| 提权防护 | admin 角色不开放自助注册；管理员不能禁用/降级自己 |
| 设备接入 | HTTP 上报需 `X-Device-Token`；MQTT 走 Broker 侧认证 |
| 重复提交 | 创建订单支持 `Idempotency-Key`；支付回调按第三方交易号去重 |
| 并发写 | 订单状态流转使用 `version` 乐观锁，冲突返回 409 而非覆盖 |
| 支付回调 | 沙箱模式简化处理；生产需接入支付宝 RSA2 验签并校验金额与商户号 |
| 实时通道 | WS 允许匿名只读（大屏），携带无效 token 则拒绝握手 |
| CORS | 白名单来自 `CORS_ORIGINS`，不再全开 |
| 密钥管理 | `.env` 不入库（`.gitignore`），模板见 `.env.example` |

## 十二、设备接入设计

- **硬件方案**：ESP32 + DHT22（温湿度）+ GPS + 门磁/电流采样，MicroPython 定时采集
- **上报协议**：
  - MQTT 主题 `iot/{device_code}/data`，JSON 载荷（兼容旧格式）
  - HTTP `POST /api/v1/iot/data`，需设备令牌，适合单点快速接入
  - HTTP `POST /api/v1/iot/telemetry`，窄表批量上报，单次 ≤50 点位，推荐新设备使用
- **点位字典**：内置 11 类点位（温度/湿度/门磁/电流/功率/电量/CO₂/信号/振动等），未注册点位返回 400；可通过 `/api/v1/iot/devices/{device_code}/points` 注册自定义点位
- **幂等与补传**：唯一键 `(device_id, point_key, ts)`，断网恢复后可按时间顺序补传，不会产生重复数据
- **状态语义**：`status` 表示可用性，`quality` 表示数据新鲜度；离线与降级由后台任务与遥测链路共同推导
- **绑定关系**：设备通过 `resource_id` 关联资源，一个资源可挂多台设备；孪生节点通过 `twin_bindings` 绑定具体点位
- **离线判定**：后台每 30 秒扫描，`last_seen_at` 早于 `DEVICE_OFFLINE_SECONDS`（默认 90 秒）即置离线
- **模拟器**：`iot/simulator.py` 每 3 秒为 4 台虚拟设备生成温湿度与坐标，支持 `MQTT_HOST` / `MQTT_PORT` / `PUBLISH_INTERVAL` 环境变量
