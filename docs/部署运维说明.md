# 部署与运维说明

怀化国际陆港冷链资源智能撮合平台（实验室硬件原型 + 港区规模虚拟） —— 生产部署、日常运维与故障排查手册。

## 一、系统概览

### 1.1 服务拓扑

```
                     ┌──────────────┐
   浏览器  ────────► │  frontend    │  Nginx 1.27（静态站点 + 反向代理）
                     │   :80        │
                     └──────┬───────┘
                /api/*      │      /ws/*（Upgrade）
                            ▼
                     ┌──────────────┐        ┌──────────────┐
                     │  backend     │◄──────►│    mysql     │
                     │  FastAPI     │        │  MySQL 8.0   │
                     │  :8000       │        └──────────────┘
                     │  单进程       │◄──────►┌──────────────┐
                     │              │        │    redis     │
                     └──────┬───────┘        │  Redis 7     │
                            │ MQTT 订阅       └──────────────┘
                            ▼
                     ┌──────────────┐◄────── ┌──────────────┐
                     │    emqx      │        │  simulator   │（可选，仅演示）
                     │  EMQX 5.7    │        │  模拟传感器   │
                     └──────────────┘        └──────────────┘
```

### 1.2 容器与端口

| 服务 | 容器名 | 内部端口 | 宿主机端口（可配） | 说明 |
|---|---|---|---|---|
| frontend | hhlg-frontend | 80 | `${HHLG_WEB_PORT:-8080}` | 运营管理端（Web 控制台） |
| demand | hhlg-demand | 80 | `${HHLG_DEMAND_PORT:-8081}` | 需求端 uni-app H5（找资源 / 下单 / 我的订单） |
| backend | hhlg-backend | 8000 | `${HHLG_API_PORT:-8010}` | 直连调试用，生产可关闭 |
| mysql | hhlg-mysql | 3306 | `${HHLG_MYSQL_PORT:-3307}` | 数据持久化到命名卷 |
| redis | hhlg-redis | 6379 | 不对外 | 缓存 |
| emqx | hhlg-emqx | 1883 / 18083 | `${HHLG_MQTT_PORT:-1884}` / `${HHLG_EMQX_DASH_PORT:-18084}` | MQTT Broker 与控制台 |
| simulator | hhlg-simulator | — | — | `--profile demo` 才启动 |

> 默认端口已避开常见占用（8000、1883、6379 常被其他项目使用）。如冲突，改根目录 `.env` 即可。

## 二、前置要求

- Docker Engine 24+（含 Docker Compose v2）

## 三、首次部署

```bash
# 1. 准备环境变量（务必修改密钥）
cp .env.example .env
#    编辑 .env，至少修改 JWT_SECRET、MYSQL_ROOT_PASSWORD、MYSQL_PASSWORD、EMQX_DASH_PASSWORD

# 2. 构建并启动全部服务
docker compose up -d --build

# 3. 等待健康检查通过（约 1–2 分钟，MySQL 首次初始化较慢）
docker compose ps

# 4. 验证
curl http://localhost:8080/api/health
# 期望：{"status":"ok","app":"怀化国际陆港冷链资源智能撮合平台","iot_mode":"lab-prototype",...}
```

首次启动时后端会自动执行 `alembic upgrade head` 建表，无需手工建库建表。

需要演示用的模拟传感器数据时：

```bash
docker compose --profile demo up -d
```

访问入口：

| 用途 | 地址 |
|---|---|
| 数字孪生大屏 / 运营管理 | http://localhost:8080 |
| API 健康检查 | http://localhost:8080/api/health |
| EMQX 控制台 | http://localhost:18084（用户 `admin`，密码为 `.env` 中 `EMQX_DASH_PASSWORD`） |

## 五、日常运维

### 5.1 启停与状态

```bash
docker compose ps                    # 查看状态（带 healthy 标记）
docker compose up -d                 # 启动
docker compose up -d --build         # 重新构建并启动（代码更新后）
docker compose restart backend       # 只重启某个服务
docker compose stop                  # 停止（容器保留）
docker compose down                  # 停止并删除容器（数据卷保留）
docker compose down -v               # ⚠️ 连数据卷一起删除，MySQL 数据会丢失
```

### 5.2 日志

```bash
docker compose logs -f backend       # 跟踪后端日志
docker compose logs --tail 200 frontend
docker compose logs -f emqx
```

后端关键日志：
- `[mqtt] connected ... subscribing iot/+/data` —— MQTT 订阅成功
- `INFO [alembic.runtime.migration] Running upgrade ...` —— 迁移执行
- `[hub] 投递异常` —— WebSocket 广播异常
- `[outbox] 事件 %s 投递失败` —— 事务外盒事件投递失败（重试 5 次后置 failed）

### 5.3 健康检查

```bash
curl http://localhost:8080/api/health     # 后端（经运营端反代）
curl -I http://localhost:8080/            # 运营管理端
curl -I http://localhost:8081/            # 需求端 H5
docker inspect --format "{{.State.Health.Status}}" hhlg-backend
```

`docker compose ps` 中若出现 `unhealthy`，先看 `docker compose logs <服务>`。

### 5.4 滚动更新

```bash
git pull
docker compose build backend frontend demand
docker compose up -d backend frontend demand
```

后端启动时会自动执行未应用的数据库迁移。

### 5.5 业务链路自检

```bash
# 1) 幂等下单：同一 Idempotency-Key 重复提交只生成一单
curl -X POST http://localhost:8080/api/v1/orders \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -H "Idempotency-Key: selftest-001" \
  -d '{"resource_id":1,"start_time":"2026-01-01T08:00:00","end_time":"2026-01-02T08:00:00"}'
# 重复执行应返回同一订单号；首次进行中并发请求返回 409

# 2) 履约流转（供给方/管理员）
curl -X PUT "http://localhost:8080/api/v1/orders/1/status?new_status=confirmed" \
  -H "Authorization: Bearer $TOKEN"

# 3) 沙箱支付：创建意图后访问 pay_url（mock-checkout）即视为支付成功
curl -X POST http://localhost:8080/api/v1/payments/1/intent -H "Authorization: Bearer $TOKEN"

# 4) 结算单与按日对账（管理员）
curl http://localhost:8080/api/v1/settlements -H "Authorization: Bearer $TOKEN"
curl "http://localhost:8080/api/v1/settlements/reconciliation?day=2026-01-02" \
  -H "Authorization: Bearer $TOKEN"

# 5) 孪生快照（大屏只读）
curl "http://localhost:8080/api/v1/twin/snapshot?alert_limit=20&event_limit=20"
curl http://localhost:8080/api/v1/twin/spaces
```

outbox 积压检查：

```sql
SELECT status, COUNT(*) FROM outbox_events GROUP BY status;
SELECT id, event_type, retry_count, last_error FROM outbox_events
WHERE status <> 'published' ORDER BY id DESC LIMIT 20;
```

## 六、数据库迁移（Alembic）

表结构完全由 Alembic 管理，应用启动**不会**自动建表。

当前迁移链：`0001_initial`（业务主表）→ `0002_alert_rules` → `0003_audit_logs` → `0004_ota_tasks` → `0005_platform_v2`（幂等键、事务外盒、空间、遥测、设备事件、支付事件、结算单、点位字典、孪生节点与绑定）。

迁移后共 20 张表，`0005_platform_v2` 为平台化能力表的统一切入点。

```bash
# 查看当前版本
docker compose exec backend alembic current

# 查看迁移历史
docker compose exec backend alembic history

# 应用全部迁移（后端容器启动时也会自动执行）
docker compose exec backend alembic upgrade head

# 回滚一个版本
docker compose exec backend alembic downgrade -1

# 修改模型后生成新迁移（生成后务必人工检查）
docker compose exec backend alembic revision --autogenerate -m "add xxx field"
docker compose exec backend alembic upgrade head
```

注意事项：

- `alembic.ini` 必须保持**纯 ASCII**（Windows 下 Python 以 GBK 读取配置，中文会抛 `UnicodeDecodeError`）
- 迁移脚本位于 `backend/alembic/versions/`，需随代码一起提交
- 已有数据的环境接入 Alembic 时用 `alembic stamp head` 打基线，不要直接 `upgrade`

## 七、设备接入

### 7.1 MQTT 上报（推荐）

| 项 | 值 |
|---|---|
| Broker | `localhost:1884`（容器内为 `emqx:1883`） |
| Topic | `iot/{device_code}/data` |
| Payload | JSON |

```json
{
  "device_code": "CW-01",
  "temperature": -18.5,
  "humidity": 62.3,
  "longitude": 110.42,
  "latitude": 27.55
}
```

后端订阅 `iot/+/data`，收到后：写库 → 更新 Redis 最新值（TTL 5s）→ WebSocket 推送到大屏。

> ESP32 + DHT22 实机固件与接线步骤见 [`iot/firmware/README.md`](../iot/firmware/README.md)：
> 修改 WiFi/服务器地址后上传 `main.py` 即可，MQTT 不通时会自动降级为 HTTP 上报。

### 7.2 HTTP 上报（备选）

```bash
# 令牌值见根目录 .env 的 DEVICE_INGEST_TOKEN；未配置该变量时可省略此请求头
curl -X POST http://localhost:8080/api/v1/iot/data \
  -H "Content-Type: application/json" \
  -H "X-Device-Token: <DEVICE_INGEST_TOKEN>" \
  -d '{"device_code":"CW-05","temperature":-17.2,"humidity":60.1}'
```

配置了 `DEVICE_INGEST_TOKEN` 时，缺失或错误的令牌会返回 401。

### 7.3 遥测批量上报（推荐新设备使用）

```bash
curl -X POST http://localhost:8080/api/v1/iot/telemetry \
  -H "Content-Type: application/json" \
  -H "X-Device-Token: <DEVICE_INGEST_TOKEN>" \
  -d '{
    "device_code": "CW-05",
    "firmware_version": "1.1.0",
    "items": [
      {"point_key": "temp_in", "value": -18.5, "ts": "2026-01-01T10:00:00"},
      {"point_key": "hum_in",  "value": 62.3,  "ts": "2026-01-01T10:00:00"},
      {"point_key": "door",    "value": false, "ts": "2026-01-01T10:00:00"}
    ]
  }'
```

- 单次最多 50 个点位；点位键必须在内置字典（temp_in / temp_deep / temp_supply / hum_in / door / current_a / power_w / battery / co2 / rssi / vibration）中，或已通过点位接口注册，否则返回 400
- 按 `(device_id, point_key, ts)` 去重，断网补传可安全重放
- 查询读模型：

```bash
curl http://localhost:8080/api/v1/iot/devices/CW-05/state      # 状态 + 质量 + 全部点位最新值
curl http://localhost:8080/api/v1/iot/devices/CW-05/points     # 点位字典
curl "http://localhost:8080/api/v1/iot/devices/CW-05/series?point_key=temp_in&minutes=60"
curl http://localhost:8080/api/v1/iot/devices/CW-05/events     # 门磁/告警/OTA 事件
```

### 7.4 设备与资源绑定

设备通过 `resource_id` 关联到资源（冷链箱/仓库），绑定后大屏点击箱体即可看到该设备的温湿度。

```bash
# 登录拿到 token
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<账号>","password":"<密码>"}' | grep -o '"access_token":"[^"]*' | cut -d'"' -f4)

# 查看设备
curl http://localhost:8080/api/v1/devices -H "Authorization: Bearer $TOKEN"

# 单台绑定到资源 ID=1
curl -X PUT http://localhost:8080/api/v1/devices/1 \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"resource_id":1}'

# 批量：把未绑定设备按序绑定到可用冷链箱
curl -X POST http://localhost:8080/api/v1/devices/auto-bind -H "Authorization: Bearer $TOKEN"
```

### 7.5 告警阈值

阈值按「资源级规则 → 全局规则（`resource_id=0`）→ 配置默认值」优先级生效：

- 温度 < -30℃ 或 > -5℃ → `critical`
- 湿度 > 90% → `warn`
- 同设备同类型告警 10 分钟内只记一条

`/api/v1/iot/telemetry` 链路另有去抖：连续 3 个采样同向越限才产生告警，数值回到正常区间自动关闭事件与活动告警。

### 7.6 批量导入与固件 OTA

CSV 表头固定为 `device_code,device_type,resource_id,firmware_version`，仅 `device_code` 必填：

```bash
cat > devices.csv <<'EOF'
device_code,device_type,resource_id,firmware_version
CW-01,dht22,1,1.0.0
CW-02,dht22,2,1.0.0
EOF

curl -X POST http://localhost:8080/api/v1/devices/import \
  -H "Authorization: Bearer $TOKEN" -F "file=@devices.csv"
# → {"created":2,"skipped":0,"failed":0,"errors":[]}
```

批量升级（`device_ids` 省略表示全部设备）：

```bash
curl -X POST http://localhost:8080/api/v1/devices/ota \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"target_version":"1.1.0"}'
```

平台向 `iot/{device_code}/cmd` 发布 `{"action":"ota","task_id":1,"target_version":"1.1.0"}`；
设备完成升级后调用 `POST /api/v1/devices/ota/report`（请求头 `X-Device-Token`）回执，
后端更新 `firmware_version` 与任务状态。模拟器默认自动回执成功：

```bash
API_BASE=http://localhost:8080 DEVICE_TOKEN=<DEVICE_INGEST_TOKEN> \
MQTT_HOST=localhost python iot/simulator.py
```

固件端已实现完整的文件级升级链路（`iot/firmware/ota.py`）：设备收到指令后拉
`GET /api/v1/devices/ota/manifest/{version}` 取得文件清单与 sha256，再逐个
`GET /api/v1/devices/ota/file/{version}/{filename}` 下载、校验并覆盖，成功后写 `version.txt` 并重启。
打包发布：

```bash
python iot/tools/make_release.py 1.1.0
# → iot/firmware/releases/1.1.0/{manifest.json, main.py, ota.py}
```

`config.py` / `boot.py` 永不分发（节点身份、引脚、WiFi、令牌留在本地）；Docker 部署时
`./iot/firmware` 以只读方式挂载到容器 `/app/fw`，并通过 `FW_REPO_DIR=/app/fw/releases` 暴露给后端。

## 八、故障排查

### 8.1 镜像拉取慢 / 超时

现象：`docker compose build` 长时间卡在 `Pulling fs layer`。

处理：
- 为 Docker Desktop 配置镜像加速（Settings → Docker Engine 的 `registry-mirrors`）
- 前端 npm 依赖已默认走 `registry.npmmirror.com`，可用 `NPM_REGISTRY` 覆盖
- 可先单独预拉基础镜像：`docker pull python:3.12-slim`、`docker pull node:22-alpine`、`docker pull nginx:1.27-alpine`

### 8.2 构建时报 Debian 源不可达

现象：`backend` 构建失败于 `apt-get update ... 404 / Connection failed`。

原因：当前后端镜像**不依赖 apt**（健康检查使用 Python 标准库）。若你在 Dockerfile 中新增了 `apt-get`，请改为不依赖系统包的方式，或先解决容器出网/代理问题。

### 8.3 `docker` 命令连不上引擎

现象：`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`。

处理：
- 确认 Docker Desktop 已启动完成（托盘图标为运行状态）
- 若 `desktop-linux` 上下文未就绪，可临时改用默认上下文：`docker --context default ps`

### 8.4 端口被占用

现象：`Bind for 0.0.0.0:xxxx failed: port is already allocated`。

处理：改根目录 `.env` 中对应端口后 `docker compose up -d`：

```ini
HHLG_WEB_PORT=8090
HHLG_DEMAND_PORT=8091
HHLG_API_PORT=8011
HHLG_MQTT_PORT=1885
```

### 8.5 页面能开但接口 404 / 数据为空

排查顺序：

1. `docker compose ps` 看 backend 是否 `healthy`
2. `docker compose logs backend --tail 100` 看是否有异常
3. `curl http://localhost:8080/api/health`
4. 确认 frontend / demand 的 `nginx.conf` 中 `/api/` 指向 `http://backend:8000`

### 8.6 大屏实时数据不动

1. 确认 MQTT 已连接：日志出现 `[mqtt] connected`
2. 确认有数据源：`docker compose --profile demo up -d` 或真实设备在发 `iot/{code}/data`
3. 直接查库：`curl http://localhost:8080/api/v1/iot/data?limit=5`
4. WebSocket 检查：浏览器控制台是否有 `[WS] 已连接`

### 8.7 修改代码后行为没变化

- 后端容器**没有**热重载，需 `docker compose up -d --build backend`
- 前端是构建产物，需重建镜像
- 开发模式（`uvicorn --reload` + `vite`）才有热更新

### 8.8 PowerShell 里中文显示成乱码

现象：`Invoke-RestMethod` 输出 `å·é¾ç®±ä½`。

原因：Windows PowerShell 5.1 把 UTF-8 响应按 Latin-1 解码，**只是显示问题**，接口与数据库数据正常。用 Python 校验：

```bash
python -c "import requests;print(requests.get('http://127.0.0.1:8010/api/v1/resources/1').json()['name'])"
```

### 8.9 创建订单返回 409

- 同一 `Idempotency-Key` 的首次请求仍在处理中：等待后重试，或换新键
- 订单状态流转并发冲突（`version` 乐观锁）：刷新订单后重试
- 资源被占用：资源已被其他活跃订单锁定，换资源或等待释放

### 8.10 outbox 事件积压 / 投递失败

1. 查积压：`SELECT status, COUNT(*) FROM outbox_events GROUP BY status;`
2. `failed` 事件看 `last_error`，多为 WS 广播异常或数据库连接问题
3. 处理后可将失败事件重置重投：

```sql
UPDATE outbox_events SET status='pending', retry_count=0 WHERE status='failed';
```

后台投递任务随后会重新拉取（单批 100，失败 5 次置 failed）。

### 8.11 设备在线但数据不动 / 状态异常

- `quality=stale/bad`：数据新鲜度不足或取值异常，检查设备上报时间与点位取值
- `status=degraded`：设备在线但数据质量差，或孪生节点绑定了 stale 点位
- `status=alarm`：存在未恢复的活动告警，处理后可调 `POST /api/v1/iot/alerts/{id}/resolve`
- `status=offline`：`last_seen_at` 超过 `DEVICE_OFFLINE_SECONDS`，检查网络与上报频率

### 8.12 支付成功但订单未更新

1. 确认 `PAYMENT_MODE=sandbox` 且访问的是返回的 `pay_url`
2. 查 `payment_events` 是否有对应 `provider_txn_id` 记录（唯一约束会去重重复回调）
3. 查订单 `payment_status` 是否为 `paid`；`waived`（免支付）场景需业务侧确认
4. 生产接入支付宝时需配置 `ALIPAY_APP_ID` / `ALIPAY_GATEWAY`，并补 RSA2 验签

### 10.1 启用 HTTPS / WSS

前端 WebSocket 地址会按页面协议自动切换为 `wss://`，只需为 Nginx 增加 TLS：

1. 将证书挂载到容器，例如 `./certs:/etc/nginx/certs:ro`
2. 在 `nginx.conf` 增加 443 server 块并复用现有 `location` 配置
3. 增加 80 → 443 跳转
4. 将 443 端口加入 frontend 的 `ports`
